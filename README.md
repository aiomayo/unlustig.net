# unlustig.net

Client-side Minecraft modpack, managed with [packwiz](https://packwiz.infra.link/)
and published automatically to Modrinth, CurseForge and GitHub Releases.

The server runs **Folia 26.2** with plugins. Folia loads *plugins*, not Fabric
mods, so everything here is **client-only** — it is what players install. The
server-side counterparts (Simple Voice Chat plugin, ViaVersion, …) are managed on
the server, not in this repository.

## Contents

| Mod | Why |
|---|---|
| [Simple Voice Chat](https://modrinth.com/mod/simple-voice-chat) | The reason the pack exists — client half of the server's voice chat plugin |
| [Distant Horizons](https://modrinth.com/mod/distanthorizons) | LOD terrain — renders the world far beyond the server's view distance |
| [Fabric API](https://modrinth.com/mod/fabric-api) | Baseline Fabric library |

Distant Horizons ships **beta builds only** — all 428 of its Fabric releases are
marked beta, so this is its normal release channel, not a pre-release warning.
It is added as `side = "client"`: it has an optional server component, but Folia
loads plugins rather than Fabric mods, so the client generates its own LOD data
from what it has seen.

Deliberately minimal. Simple Voice Chat declares no *required* dependencies — its
Modrinth entries for Mod Menu, Cloth Config, ViaFabric, Sound Physics, AudioPlayer,
LuckPerms and Vanish are all `optional` — so performance and convenience mods are
left to players rather than forced through the pack.

```
pack.toml            # name, version, MC + loader version, options
index.toml           # generated by `packwiz refresh` -- commit it
mods/*.pw.toml       # one file per mod: URL + hash, no jars in git
.packwizignore       # excludes repo metadata and exports from pack exports
```

The pack lives at the repository root, matching the
[official example pack](https://github.com/packwiz/packwiz-example-pack). packwiz
treats its directory as the pack, so `README.md` and `.github/` are excluded via
`.packwizignore` rather than by living outside it.

## Versions and loaders

The pack targets whatever the server runs — currently **Minecraft 26.2 on
Fabric**. Two deliberate decisions:

**Version range** uses packwiz's native mechanism rather than parallel packs:

```bash
packwiz settings acceptable-versions -a 26.1     # or: -r 26.1 to remove
```

This writes `[options] acceptable-game-versions` in `pack.toml` and widens which
mod *files* packwiz accepts when adding and updating, so a mod whose newest build
still targets 26.1 can be used in a 26.2 pack. The pack itself remains a 26.2
pack — `versions.minecraft` is unchanged — so this is a resolution filter, not a
multi-version build.

**It is therefore not a publishing input.** Releases advertise
`versions.minecraft` alone, because that is what the exported `.mrpack` manifest
pins. Listing 26.1 as a supported game version would promise compatibility the
artifact does not deliver — a 26.1 player would install the pack and receive a
26.2 manifest. `validate.yml` enforces this by comparing the published version
against the built manifest.

**One loader only.** packwiz supports exactly one loader per pack; `packwiz init
--modloader "fabric,neoforge"` is rejected outright ("Given mod loader is not
supported"). This is not a packwiz limitation but a format one: a `.mrpack`
manifest declares a single `fabric-loader` **or** `neoforge` dependency. Shipping
NeoForge as well would mean a second pack directory and a CI matrix, so it is
deliberately not done here.

To move the pack to a new Minecraft or loader version, use the built-in migration
commands rather than editing `pack.toml` by hand:

```bash
packwiz migrate minecraft 26.3
packwiz migrate loader latest        # or: <version> | recommended
```

## Repository conventions

Following the [official git guidance](https://packwiz.infra.link/tutorials/creating/git/)
and the [example pack](https://github.com/packwiz/packwiz-example-pack):

- **`.gitattributes` (`* -text`)** — disables Git line-ending conversion. Without
  it, checking out on Windows rewrites line endings, which changes the hashes
  recorded in `index.toml` and makes installs fail with invalid-hash errors. If
  added to an existing clone, run `git add --renormalize .` afterwards.
- **`.packwizignore`** — same syntax as `.gitignore`, but excludes files from
  *pack exports*: repo metadata (`/README.md`, `/.github/`) and previous builds
  (`*.mrpack`, `*.zip`, which also covers the CI `dist/` directory).
- **`.gitignore`** — keeps `*.mrpack` / `*.zip` exports out of history.
- **`no-internal-hashes = true`** in `pack.toml` — omits per-file hashes from
  `index.toml`. Without it, every mod change rewrites a hash per file plus the
  index hash in `pack.toml`, which is the usual source of merge conflicts in a
  packwiz repo. The hashes are not lost, only deferred: CI runs `packwiz refresh
  --build` to regenerate them at export time, reproducing an identical index hash.

  So **`packwiz refresh --build` is required before exporting**. A plain `packwiz
  refresh` leaves the index hashless, which is correct for committing but not for
  distribution.

packwiz rewrites `pack.toml` whenever it changes a setting, so comments placed in
that file do not survive — decisions are documented here instead.

## Working on the pack

Requires packwiz on `PATH` (`go install github.com/packwiz/packwiz@latest` —
upstream publishes no prebuilt binaries and has no tagged releases, so it must be
built from source).

All commands run from the repository root:

```bash
packwiz mr add <slug>        # add from Modrinth (also accepts a URL, ID or search)
packwiz cf add <slug>        # add from CurseForge
packwiz github add <owner/repo>   # add from GitHub releases
packwiz url add <name> <url>      # add from a direct link

packwiz list -v              # list mods with resolved filenames
packwiz update --all         # update every mod
packwiz pin <mod>            # hold a mod at its current version
packwiz remove <mod>         # remove a mod
packwiz refresh              # rebuild index.toml -- always before commit
```

Set `side = "client"` on new mods; packwiz defaults many entries to `both`.
Mods can also be marked optional in their `.pw.toml`:

```toml
[option]
optional = true
default = false
description = "Shown when the user picks optional mods"
```

Test an export locally before tagging:

```bash
packwiz refresh --build && packwiz modrinth export -o /tmp/test.mrpack
```

## Validation

`.github/workflows/validate.yml` runs on every push and pull request, and is
declared with `on: workflow_call` so the release pipeline reuses the identical
job rather than duplicating checks. `release.yml` gates publishing behind
`needs: validate`, so a failing check blocks the release before anything reaches
Modrinth or CurseForge.

The checks, in order:

1. **`pack.toml` structure** — required keys present, exactly one mod loader.
2. **Index freshness** — `packwiz refresh` must produce no diff, catching a
   hand-edited or uncommitted `index.toml`.
3. **Mod metadata** — every `.pw.toml` has a name, filename, `[download]` with a
   URL (or `metadata:curseforge` mode) and hash, and `side = "client"`.
4. **Exports build** — both `.mrpack` and the CurseForge zip.
5. **Artifacts verified** — archives open, the mrpack manifest's Minecraft
   version and loader match `pack.toml`, the file count matches the mod count,
   and every entry is client-required with downloads and hashes.
6. **Publish inputs** — the `game-versions` and `loaders` values the release
   workflow derives from `pack.toml` are non-empty, free of percent-encoding,
   and the published game version matches the `minecraft` dependency in the
   built `.mrpack` manifest.
7. **No metadata leaks** — neither archive contains `README.md`, `.github/`,
   `dist/` or `.git`.

Checks 3 and 5 exist because of two verified packwiz behaviours: `packwiz
refresh` **accepts** a `.pw.toml` with no `[download]` block and exits 0, with
the export panicking only later; and a failed export still leaves a **0-byte**
file behind, so checking that an artifact merely exists is not enough.

Check 6 exists because a real release failed at upload with *"At least one game
version should be specified"*: the metadata step was percent-encoding a
multi-value output as `26.1%0A26.2`, a convention required by the `set-output`
command GitHub removed in 2022. The `$GITHUB_OUTPUT` file that replaced it does
not decode `%0A`, so mc-publish received the literal string. Publish inputs are
now validated before a tag can reach the publish step.

## Releasing

```bash
git tag v1.0.0 && git push --tags
```

CI then exports `.mrpack` and a client-side CurseForge `.zip`, publishes both to
Modrinth and CurseForge with the correct `game-versions`/`loaders` read from
`pack.toml`, and attaches them to a GitHub Release with a generated mod list.

`workflow_dispatch` runs the same build with `dry-run: true` by default —
artifacts are produced and attached to the run, but nothing is published.

### Distribution targets

Modrinth, CurseForge and GitHub Releases are the complete set worth automating.
FTB's API is read-only and its packs are curated by their team; Technic has no
upload API (self-hosted zip plus a web form). Neither can be published to
programmatically.

## CI secrets

- `MODRINTH_ID`, `MODRINTH_TOKEN`
- `CURSEFORGE_ID`, `CURSEFORGE_TOKEN`

`GITHUB_TOKEN` is provided automatically. CurseForge export is best-effort: mods
sourced from Modrinth with no CurseForge project get embedded as raw jars and
need manual CurseForge staff approval per release, so a CurseForge failure never
blocks the Modrinth release.
